# Later

Ideas the developer has said he'll build later. Claude Code adds to this list whenever one comes up and reviews it at the end of each step.

| Idea | Raised | Notes |
| --- | --- | --- |
| **LLM map editor**: fix the map by typing instructions to an LLM instead of clicking a graph editor. Code still enforces the hard rules (no loops, no arrows to missing concepts). | Step 7 | The diary already supports it (`actor: "editor"`, `instruction`, `request_id`). Added to `docs/build-plan.md` Step 10, which decides whether it replaces click editing. |
| **Graph-generating model**: a trained model that builds concept maps, in place of (or alongside) the prompted extractor. | Step 8 | Training data: extraction outputs and your corrections in `map_event` (Step 9 uses a judge, not gold maps, so corrections are the human-checked data). Compare against prompting with the Step 9 harness. Same idea as After-the-MVP item 1. |
| **Session graphs**: a diagnosis pulls its starting point from the global graph, the session builds its own graph, and the global graph is updated from it afterward. | Step 8 | Design in Steps 11–13. Proposed answer to the open question (Step 9 discussion): a view computed at session start (the tutor briefing, K7), not a stored copy. Inside a session the tutor works in steps typed by the concept's kind (reasoning steps for `concept`, solution steps for `skill`, condition → choice for `decision`), generated from the briefing and not stored. |
| **Other model providers** (OpenAI, Google, and the like) in the settings tab, beside the Claude models. | Step 9 | Settings already store a model per job (generation, teaching, evaluation). Needs a provider-neutral call layer in place of `callClaude`, and per-provider prices. |
| **Side-by-side judging of two prompt versions**: the judge sees both maps of a case and picks the better, then again with the order swapped; a win counts only if both agree. | Step 9 | Until then, versions are compared by majors per 10 concepts. |
| **Very large sources** (a whole textbook): one extraction call may run out of output room (64K tokens) for a few hundred concepts and their arrows. | Step 9 | Likely fix: extract chapter by chapter, reusing ids across chunks the way courses already share concepts. |
| **Test the map judge with planted errors**: take one map checked by hand, plant one known error per copy (delete a prerequisite, reverse an arrow, delete a concept, move a target depth by 2, flip a role; plus hand-written off-topic concepts and synonym duplicates), and score how many the judge catches and how many problems it flags on the untouched map. | Step 9 | Until this runs, judge scores are unverified. Proposed bar: catches at least 80% of planted major errors, at most 2 false major problems on the clean map. A catch = right problem type on the right concept ids. |
| **Clarifier eval**: measure whether the clarifying questions are the ones that change the map most (the map eval uses fixed answers, so it never tests the clarifier). | Step 9 | Possible method: a simulated learner answers from a short persona; compare map quality with and without the questions. |
| **Concept-reuse eval**: run cases in a row in one graph and measure whether a second goal reuses the first goal's concept ids instead of duplicating them (G2). | Step 9 | Eval cases run in separate graphs today (M6). |
| **Separate identity step for concept reuse** (from LearnHarness's auditor): after extraction, a second call that never sees the source decides which new concepts are existing ones. | Step 9 | Only if the concept-reuse eval shows the extractor duplicating concepts. Per concept the candidate list is short, so no search index is needed. |
| **Held-out eval case**: keep one case you don't tune prompts against, and score it only now and then, so prompts don't end up fitted to the few cases you look at. | Step 9 | Same idea as a train/test split. Worth doing once there are 3+ real cases. |
| **Learning-curve checks**: once there's evidence, plot error rate against practice for each concept@depth (or tutoring step); a curve that doesn't fall smoothly means the unit is drawn wrong. | Step 9 | Needs weeks of evidence: Step 15 or later. |
| **Forgetting and timed review** (K5): mastery doesn't fade yet; reviews just favor the concept tested longest ago. | Step 9 | Memory system K1–K8 was built in Steps 11–13 (migration `006_learner_model.sql`). Add a forgetting curve once there's evidence to fit it to. Same as After-the-MVP "timed review". |
| **Fit the mastery parameters** (prior, learn, guess, slip) from your own evidence, maybe per depth, instead of the starting guesses. | Step 11 | Defaults in `packages/core/src/mastery.ts`. Fit by maximum likelihood over the evidence log once there are a few hundred answers. |
| **Calibration report**: from `predicted_p` on every evidence row (K8), bin predictions and compare with the share actually right. | Step 11 | The data is recorded from the first answer; only the report is missing. A well-calibrated model's 70% predictions come true 70% of the time. |
| **Answers passed down count as much as direct ones**: a right answer on B@2 updates A@1 with the same guess and slip as a question on A@1 itself. | Step 11 | Strictly it's weaker evidence. A discount (a higher guess for passed-down readings) is one parameter; decide once calibration shows over-confidence on inferred concepts. |
| **Grader mistakes in the mastery math**: you chose to count LLM grades as certain. The noisy-sensor version uses the grader eval's false-pass and false-fail rates as extra guess and slip. | Step 11 | Revisit once the grader eval has measured those rates on your own labeled answers. |
| **Item writer eval** (rule 7): nothing yet measures whether the diagnostic's questions test the depth asked, stand alone, and avoid testing prerequisites instead. Same for the session summarizer. | Step 12 | Likely a judge prompt with a per-depth rubric over a set of written questions, like the map judge. |
| **Auto-graded questions**: numeric or choice answers checked by code (`grader: 'auto'` in the schema), no LLM call. | Step 12 | The evidence table already has the column; the item writer would need an answer format. |
| **Simulated learner for the tutor eval**: scripted turns don't adapt to what the tutor asks. A Claude-played learner from a short persona (what they know, a misconception) would test fit, not just habits. | Step 13 | Same idea as the clarifier eval's simulated learner. |
